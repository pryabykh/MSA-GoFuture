### <a name="_b7urdng99y53"></a>**Название задачи: Схема репликации данных между регионами**

### <a name="_uanumrh8zrui"></a>**Дата: 9 мая 2026**

### <a name="_3bfxc9a45514"></a>**Контекст**

Платформа GoFuture предоставляет высоконагруженный сервис заказа поездок с требованиями:

- обработка более 500 000 конкурентных поездок
- 99.99% доступности
- низкая задержка для пользователей в Юго-Восточной Азии
- устойчивость к региональным отказам
- возможность масштабирования и соблюдения локальных регуляторных требований.

Данные платформы распределены между несколькими доменными сервисами (Booking, Payments, Driver, Pricing и др.), каждый
из которых имеет собственное хранилище данных.
Необходимо определить стратегию репликации данных между регионами с учётом требований к согласованности, задержке и
отказоустойчивости.

### <a name="_3bfxc9a45514"></a>**Требования**

- Исключить единую точку отказа для критических данных.
- Минимизировать влияние межрегиональной задержки на пользовательские операции.
- Обеспечить предсказуемое поведение системы при частичных отказах.
- Обеспечить масштабируемость и управляемость схемы.

### <a name="_3bfxc9a45514"></a>**Решение**

Принята гибридная схема репликации данных, сочетающая:

- асинхронную репликацию баз данных,
- репликацию событий через Kafka,
- локальную запись данных в каждом активном регионе.

### <a name="_3bfxc9a45514"></a>**Репликация транзакционных данных (PostgreSQL)**

| Регион   | Роль       |
|----------|------------|
| Сингапур | Primary DB |
| Джакарта | Replica DB |
| Гонконг  | Replica DB |

- Запись происходит локально в регионе, обслуживающем пользователя.
- Межрегиональная репликация выполняется асинхронно.
- При конфликте используется Primary DB.

### <a name="_3bfxc[ADR_1.md](ADR_1.md)9a45514"></a>**Репликация событий (Kafka)**

**Тип репликации:**
- Репликация по критическим топикам

**Принципы:**
- Каждый регион имеет локальный Kafka-кластер.
- Топики партиционируются по региону
- Критические события реплицируются между регионами.

**Примеры реплицируемых событий:**
- BookingCreated
- BookingFinished
- PaymentCompleted
- DriverStatusChanged


**Поток данных:**
1. Пользователь создаёт заказ.
2. Booking Service пишет данные в локальную БД.
3. Доменные события публикуются в локальный Kafka.
4. Kafka MirrorMaker реплицирует события в другие регионы.


### <a name="_3bfxc[ADR_1.md](ADR_1.md)9a45514"></a>**Альтернативы**
Синхронная репликация БД

Отклонена, так как:
- увеличивает latency пользовательских операций;
- критична к межрегиональным задержкам.
