### <a name="_b7urdng99y53"></a>**Название задачи: определить очередность выделения сервисов**

### <a name="_uanumrh8zrui"></a>**Дата: 07 мая 2026**

### <a name="_3bfxc9a45514"></a>**Контекст**

Микросервисы должны быть выделены по доменным зонам без простоя системы и с минимальным влиянием на текущие
бизнес-процессы.

### <a name="_3bfxc9a45514"></a>**Требования**

- Минимизация времени простоя.
- Обеспечение непрерывной работы клиентских приложений.
- Сервисы должны быть независимыми, где это возможно.

### <a name="_3bfxc9a45514"></a>**Решение**

| Этап | Сервис         | Логика выбора                                                                                                                     |
|------|----------------|-----------------------------------------------------------------------------------------------------------------------------------|
| 1    | Booking        | Ключевой сервис, управляет жизненным циклом поездки. Наиболее загруженный.                                                        |
| 2    | Driver         | Сервис водителей напрямую связан с Booking, необходим для корректного функционирования системы.                                   |
| 3    | Pricing        | Сервис расчёта стоимости и динамического ценообразования; интеграция с Booking обязательна.                                       |
| 4    | Payments       | Сервис финансовых транзакций, зависит от Booking и Pricing; высокие риски при ошибках → выделение после основных бизнес-сервисов. |
| 5    | Geography      | Вспомогательный сервис для маршрутов и ETA, можно внедрять параллельно с Payments.                                                |
| 6    | Notification   | Сервис отправки уведомлений; Не приоритетный, можно использовать API монолита                                                     |
| 7    | Fraud          | Антифрод, зависит от событий Booking/Payments.                                                                                    |
| 8    | Analytics / BI | Последний этап — сбор и аналитика событий, отчёты для менеджеров и бухгалтеров.                                                   |

### <a name="_3bfxc9a45514"></a>**Альтернативы**

Параллельная декомпозиция всех сервисов. В этом случае повышаются риски и сложность координации.


### <a name="_3bfxc9a45514"></a>**Компромиссы**

Некоторые сервисы, как Notification и Fraud, внедряются позже. Следовательно временно используются соответствующие API монолита.
